Scope and architecture

This is a bilingual public association website, not a connected member-management application. Routing flows from app/[lang]/[[...slug]]/page.tsx to WiseTechSite → ExpansionRoute → FullInnerRoute. Static route specifications, two historical event records and 79 historical partner records are the primary data sources. Public forms are local draft or mailto flows; the member portal and membership activation are explicit previews. No active application API, database-backed member records, jobs, webhooks, payments, real AI model calls or admin CRUD were found. D1/R2 bindings are null and the database schema is empty. Optional header-based auth helpers are unused by routes.

Inventory: 138 baseline tracked files (39 non-asset files, 99 assets). Reviewed application/rendering code, routes and metadata, auth/database/example boundaries, Worker and build configuration, package manifest/lockfile, shell scripts, tests, asset references and CSS structure. Static reference checks were combined with built-Worker and production-server requests. No automatic dead-code or unused-package removal was trusted without route/peer-dependency analysis.

What changed and what remains

Added: five automated checks through the compiled Worker for remote/private image URL rejection, invalid transform parameters, SVG/HTML refusal, portal preview identity/database isolation, and reflected markup escaping. These establish existing boundaries; they are not fixes for new exploits. Added this report, a prioritized CSV tracker, a coverage matrix, route evidence and the dependency audit snapshot.

Production fixes: none, because no finding met P0 severity with current evidence and the request limits implementation to safe P0 cleanup. No packages, product routes, content, assets, database settings, access policies or deployment state were changed. Optional broader P1/P2 scope was offered during the audit; absent an answer, it was not assumed.

Engineering work that does not require product decisions: dependency compatibility updates, own-property route guards, verification repair, strict route/status validation, error recovery, and removal of proven shadowed branches. The first bounded implementation batch is WT-01, WT-02 and WT-05, followed by WT-06 and WT-13. Keep these separate from product-flow changes and rerun the full checks after each coherent change.

Product/content decisions: email draft versus actual submission for partner/member enquiries; required fields and acknowledgement wording; whether search, directory, portal and assistant controls remain previews; whether optional D1 scaffolding is retained; the authoritative public origin and public asset URL retention. Activating accounts, database writes, payments or an AI service would change scope and is not part of this cleanup.

Verification and limits

  • npm test: build succeeds; baseline content-routes suite fails. Running that file directly gives 9/10 passing, with the obsolete navigation-label assertion failing. Remaining original files pass (4 + 1 + 1 test cases).
  • node tests/security-boundaries.test.mjs: 5/5 passing; node --test tests/security-boundaries.test.mjs also exits 0. No network, real identity, or database is used.
  • npm run lint: exit 0, 0 errors and 11 pre-existing image-element warnings. tsc --noEmit --incremental false: 3 Cloudflare type errors, documented in WT-05.
  • All 68 sitemap paths in both languages (136/136) return 200 through the compiled Worker. Total bounded route sample: 150 requests, 147 responses with status 200 and 3 rejected render calls. Missing-page status is not considered a pass. Referenced local img sources and checked cross-page hash targets had no missing files/IDs in that sample.
  • npm run start -- --port 4173: server starts with local network capability; HTTP smoke checks yield homepage=200, unknown route=200, constructor route=500. Server stopped after the checks. Initial sandbox listen denial was environmental, not a repository defect.
  • npm run db:generate: succeeds, 0 tables/no schema changes. Shell scripts pass bash -n. The fresh dependency install helper was source-reviewed, not rerun: the checkout already has installed locked dependencies. Lockfile install reproducibility remains not-tested.
  • npm audit --json: 26 affected package entries. These are package-level rollups, not 26 distinct reachable exploits. The raw snapshot includes advisory URLs and fix metadata. No force update was performed.
  • Credential-signature scan of tracked text found no matching common token/private-key patterns; values were never printed. This is not proof that the repository or history has no secrets.
  • Live read-only sample: homepage returns 200 and expected content; portal profile returns 200, noindex,nofollow and “Preview only — no account or private member data is connected.” Deployment SHA was unavailable, so repository/live version equivalence is unknown.
  • Attempted live form interaction timed out without returning a session ID. No submission, prepared-email click, email send, account change or persistence result is claimed. No returned session ID was available to close. Desktop/mobile interactive UI, keyboard/focus behaviour, bulk operations, integration failures, real authenticated access and platform header stripping were not verified. Static focus/menu code exists, but no complete accessibility claim is made.
  • No Lighthouse score, field performance percentile, live workload benchmark or client-side console/network pass is claimed. Static assets and bundle/routing structure were inspected; no production load testing occurred.

Security boundaries retained

Image optimization rejects absolute, protocol-relative and private-host source URLs before asset access, and blocks SVG/HTML content. User-supplied record names are React-escaped. JSON-LD is generated from static source data, with no demonstrated untrusted-input injection. Portal previews expose no real account record and do not read the database. Enquiry mailto parameters are encoded. The optional auth helper validates relative return paths, safely decodes optional names, and depends on trusted platform header injection; it does not implement workspace membership. These observations do not certify an unused auth helper for a future direct-origin deployment.
